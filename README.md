## Collect proof of your work in the 'documentation' folder
With each step of the development process, you will have to collect proof of your work. \
This allows you to demonstrate that you have achieved one or more learning outcomes.
What’s more, it’s important for your own learning process.

It can be any type of document you create in addition to the standard md files (e.g. `REVIEW.md`, `RETROSPECTIVE.md`, `CODE_REVIEW.md` etc.).

> Examples of proof can be found in Canvas.

## The process

### Prepare

**Create a TDD (Technical Design Document)** \
On approval of the FDD, you can start writing the technical design document (TDD):
* Write a technical design document for your `Ambitieproject`:
* Describe how you're going to build it, the technologies you will use, and the architecture of the application.

** Scrum board and backlog** \
* Create a scrum board in `GitHub Projects` with these columns:
  sprint backlog (ToDo), in progress, testing, done
* Place the requirements in `GitHub Issues` (which will act as your backlog).
* Prioritize the backlog items with the MoSCoW-method. Use a label in `GitHub Issues` to indicate the priority.
* Have a Sprint Planning meeting:
  * Decide which In this meeting you need to refine each user story (issue) into smaller, more technical items.
    Each item should be clear enough that it can be realised without further discussion.
  * Then estimate which items you can do in the first sprint (in this project a sprint takes 1 week).
  * Move them to the sprint backlog column on the scrum board.

### Realise
Start a stand-up meeting every time you begin working on the project (which is probably each lesson):
* Open the scrum board
* Each team member answers these questions:
  * What did you do last time?
  * What will you do today?
  * Are there any impediments in your way?
* Update the scrum board.
* Start developing on the sprint backlog items (ToDo).

### Test
* Perform a test to verify that the application meets the requirements in the FDD.

### Review
* Show the result so far to the client (the items in the `Done` column)
* Write down feedback from the client in `REVIEW.md`.
* Add/change items in the Backlog (in Issues) based on the feedback in `REVIEW.md`.

### Retrospective
* You will have a meeting with your team (and teacher) and discuss the process of the project.
* Complete the `RETROSPECTIVE.md` in the `documentation` folder.

### Code Review
* You will review your code with your teacher.
* Write down the results in `CODE_REVIEW.md` in the `documentation` folder.
